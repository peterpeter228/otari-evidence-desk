# Owner-recorded demo rehearsal (3–5 minutes)

This is a rehearsal outline, **not an already recorded or qualifying live demo**. Contest video must use the entrant's own voice and screen. Do not use synthesized speech or generated video to impersonate the entrant.

## Before recording

- Resolve live acceptance gates and record only verified features; otherwise explicitly call it an offline prototype, not a submission-ready hosted demonstration.
- Hide dashboards showing account details, keys, payment information or unrelated tabs.
- Prepare public or synthetic sources, verified source hashes, model cards and sanitized request IDs.
- Make judge-accessible repo branch/first adapter commit and actual hosted proof available only after public-readiness review.

## Suggested sequence

1. **0:00–0:35 — Problem**: a confident comparison without traceable evidence can hide contradictions. Show the question and the three sources.
2. **0:35–1:30 — Evidence**: run the pipeline. Show exact quotes, source-supported versus contradicted versus insufficient. In the synthetic fixture say the verdicts are predefined, not AI.
3. **1:30–2:30 — Hosted architecture**: only if live verified, show two distinct open-weight model IDs and different roles, Otari request IDs, guardrail result and actual usage. A fixture cannot substitute for this segment.
4. **2:30–3:20 — Failure handling**: use a safe recorded budget/guardrail/citation rejection case; distinguish local safeguards from native Otari features. Explain pending costs freeze new calls, not zero cost.
5. **3:20–4:10 — Practical output**: inspect source provenance and export JSON/Markdown. Edit a source to demonstrate stale output clears. Explain what the app cannot establish.
6. **4:10–4:45 — Honest feedback**: answer what glue code was necessary, any temptation to bypass the gateway, whether/why you would continue using Otari. Cite real experiences only; not hypothetical tests.

## Submission checklist

Project name + one-line description; owner-entered Otari email; public repo; contest branch; first integration commit link; features actually used; actual issues/PRs (or none); own screen/voice video; written/video feedback; owner review. Never infer prize qualification or payment certainty from a successful local test.
